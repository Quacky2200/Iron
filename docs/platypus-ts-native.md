# From QuickJS to native TypeScript (platypus_ts)

This page explains, for readers who were not there, how Platypus's gameplay scripts moved from JavaScript bundled by bun and
interpreted by QuickJS to TypeScript compiled to machine code by Platypus's own compiler, platypus_ts. It says why, what changed,
how a game is written now, what the move bought in frame time, and what is still open or unverified. It summarises; the
details are in the pages it links.

## Why

- **QuickJS was too slow for script-heavy games.** QuickJS is an interpreter with no JIT. A sine demo that built meshes in
  script ran at about 30 ms a frame until the work moved to Rust; 123 fish in `examples/fishtank` took about 32 ms of
  QuickJS a frame before batching. Script cost decided how a game had to be written. The spike that started platypus_ts
  (`docs/research/platypus-ts-spike.md`) compiled a game's `sim.ts` (678 lines of game rules) and ran a 10,000-step
  benchmark of it in 8.8 ms against 406 ms in QuickJS, with the same checksum.
- **No bun and no `node_modules` for games.** A game was a bun project (`package.json`, `bun install`, `bun run build`, a
  JavaScript bundle). Building one needed the JavaScript toolchain and a dependency tree. A compiled game needs only the
  `platypus-build` tool; `tsc` is optional, for type checking while developing.
- **Declarations from Rust.** The engine's TypeScript API was written twice: once in Rust and once by hand in `js/engine`
  (and later in hand-written `.d.ts` files for the compiler). Generating the declarations from the Rust code removes the
  second copy and the drift between them.
- **Games as ordinary TypeScript.** The goal is that a game's code reads as plain TypeScript (classes, components, React
  function components, ESM modules, `async`), checked by `tsc --strict`, with engine names as globals and no engine
  imports or Platypus-specific build steps in the source. iOS forbids JIT compilation in apps (writable executable memory),
  which an interpreter sidesteps only by being slow; compiled code can be linked into the executable ahead of time
  instead (planned, see below: today's launch path is a JIT, so it does not run on iOS either).

## What changed

### The compiler and runtime

- **`tools/platypus_ts`** compiles TypeScript: oxc parses it, `lower/` infers types from the source's annotations (bottom-up,
  with the expected type pushed into literals; it trusts `tsc` and has no checker of its own) and lowers to a structured,
  typed IR (`ir.rs`), and Cranelift generates machine code (`codegen.rs`). `platypus_app` compiles a game in process with the
  Cranelift JIT at start-up (`crates/platypus_app/src/native.rs`); an `--aot` object-file path exists. See
  [platypus-ts.md](platypus-ts.md).
- **`tools/platypus_ts_rt`** is the runtime: a precise mark-sweep GC with shadow-stack roots, strings, arrays, maps, sets,
  JSON, `RegExp`, promises and timers, `Intl` pieces, and the `ts_rt_*` functions compiled code calls. A GC stress mode
  (`PLATYPUS_TS_GC=stress`) collects at every allocation in the test suite and, with the same variable, in `platypus-app` (`native.rs`).
- **Tests compare with bun.** `tools/platypus_ts_tests` (five groups: `lang`, `stdlib`, `engine`, `engine_api`, `ui`) runs
  programs natively; for the language and standard library the expected output is generated by running the same
  source with bun (`tools/platypus_ts_tests/bench/gen_*_expected.ts`).

### The engine API, declared once

- **`#[platypus_api]`** on a Rust module (`crates/platypus_api_macros`) generates the manifest, the TypeScript declarations,
  `extern "C"` shims for compiled code and typed QuickJS bindings. Math (`platypus_math`), engine services
  (`platypus_engine_api`), scenes (`platypus_scenes`), physics (`platypus_physics_api`) and rendering data (`platypus_render_api`) are
  declared this way. See [platypus-api.md](platypus-api.md).
- **No hand-written `.d.ts`.** `platypus-build types` writes `types/platypus.d.ts` from the manifests, the UI tables and the
  compiler's built-ins. The hand-written `engine_ts.d.ts` and the TypeScript `facade.ts` that bridged gaps are gone; what
  the compiler itself declares is the table `tools/platypus_ts/src/builtins.rs`. Guard tests fail if a hand-written
  declaration file comes back and compare the generated file with a blessed API snapshot
  (`tools/platypus_build/tests/golden/api_surface.txt`).
- **UI tables.** `crates/platypus_ui/src/tables` holds, as plain data, what a script can say to the UI (style properties,
  attributes, elements, event fields and `on*` props, React hook signatures). `tools/platypus_ts/src/ui_dts.rs` writes the UI
  half of the declarations from them, and `platypus_ui` tests check them against the code that applies them.

### Building games: `platypus-build`

- **`tools/platypus_build`** (`platypus-build`) has `build`, `types`, `assets`, `dev`, `check`, `init`, `package` and `bench`. A
  build resolves the module graph, runs `tsc` when present and writes `build/game.pbundle`, `game.css` and assets. See
  [platypus-build.md](platypus-build.md).
- **`project.json` only.** A game is a `project.json` (metadata, template variables, platform sections, licence; only
  `name` is required), a `tsconfig.json` and `src/`. No `package.json`.
- **Modules.** Relative imports are followed; a bare import (`from "foo"`) is a file of `src/modules/` next to the entry;
  there is no `node_modules` resolution, so a TypeScript package is used by copying its source in.
- **ESM order.** Top-level statements, including top-level `await`, run in module order in the program's `init`, as in
  ESM. `register(Class)` is an ordinary run-time call that records a component class when it runs.
- **`package`** writes one executable holding the host, the bundle, CSS, assets, icon and version info.

### Native engine pieces that scripts used to do

Under QuickJS a large part of the engine's behaviour lived in `js/engine` (TypeScript run by QuickJS). For compiled
games these are native Rust:

- **UI:** `crates/platypus_ui_native` is a React-compatible reconciler in Rust (re-render semantics, hooks, keyed diff, effects
  in React's order, portals, events) over `UiTree`; compiled JSX and hooks call it. See [ui-native.md](ui-native.md).
- **Scenes:** `crates/platypus_scenes` (`SceneManager`, `Scene`, prefabs, `instantiate`, the scene file loader and saver in the
  same format as before) and `crates/platypus_kinds` (the registry of component kinds the loader uses).
- **Physics** (`platypus_physics_api` over `platypus_physics`) and **audio** (state per thread in `platypus_engine_api`).
- **Animation:** `crates/platypus_animation` (curves, clips, pose blending, `Animation`, `Animator`). Clip curves are bound to
  their bones once per animated root instead of looked up by name every frame, Unity-style culling modes
  (`Animator.cullingMode`, `Animation.cullingType`), skinned meshes culled by their bones, and animators posed on several
  threads. See [animation-native.md](animation-native.md).
- **Render sync:** `crates/platypus_app/src/render_sync.rs` copies the compiled game's registries into the renderer each
  frame. It first rebuilt everything every frame (0.2-2 ms in 3D scenes, which made some examples slower than QuickJS);
  it is now incremental, by registry versions.
- **Windows:** `Window.create` opens extra OS windows (owned tools, dialogs, isolated windows in their own family with
  messages: `postMessage`, `request`, `broadcast`). See [windows.md](windows.md).
- **Virtual file system and asset packs:** `crates/platypus_pack` (`.ppk` packs, a `Vfs` over loose folders and packs).
  `platypus-build package --packs` puts the data files in packs; it is opt-in. See
  `docs/research/platypus-virtual-fs-plan.md` and `docs/research/platypus-asset-packs.md`.

### QuickJS deprecated

`platypus_app` refuses a QuickJS bundle (`build/game.js` without `game.pbundle`) unless `--force` is given; `platypus_editor`, whose
own UI is still QuickJS, forces implicitly. Nothing is deleted yet. The removal plan, in order, is in TODO.md
("QuickJS deprecated; removal plan"): port the editor to platypus_ts, then delete the QuickJS backend of `platypus_script`,
`platypus_native::register_quickjs`, the `js/` packages and the QuickJS fixtures and bun build paths.

## How games differ

- The compiler supports a defined subset of TypeScript, and within it aims to give JavaScript's answer. Where it does not
  (for example `null` and `undefined` are not told apart, `JSON.parse` parses into the static type, `matchAll` is eager),
  the differences are listed in [differences.md](differences.md), "Compiled TypeScript (platypus_ts)". The supported language
  in detail: [platypus-ts.md](platypus-ts.md), "Supported language".
- **Scope policy** (proposed, `docs/research/platypus-ts-type-checking.md`, section 4): a core of classes, interfaces,
  components, enums, unions, generics, closures, async, collections, destructuring and ESM; other features only when a
  shipped example or a real package needs them, each with a bun-compared test; no type-level evaluator or checker of our
  own, no decorators beyond `register` / `property`, no namespaces, `Proxy` or `eval`. Unsupported constructs are a
  compile error naming the construct, never dropped silently.
- Engine and UI names are globals from `types/platypus.d.ts`; examples import only relative files, `src/modules` files and
  CSS. Old `import { .. } from "@platypus/engine"` forms still compile.
- `any` / `unknown` as dynamic values are not built yet (see "What is next").

## Benchmark results

### Method

Every example runs in the same release host without a window (`platypus-app --bench`: an offscreen target, no vsync or frame
cap; each frame waits for the GPU work of the frame before it), at 1280x720, with a fixed step of 1/60 s per frame and the
same scripted input (`tools/bench/inputs/<name>.json`). The QuickJS side is the same example on `main`, built with its own
`bun run build`. `platypus-build bench` runs the whole batch and writes [benchmarks.md](benchmarks.md) and the raw
[benchmarks/results.json](benchmarks/results.json).

The final run (2026-10-23, commit `01c1daf1`, against `main` at `5b8aa521`): AMD Ryzen 9 5900X (12 cores, 32 GB),
NVIDIA GeForce RTX 5080 on Vulkan, Windows 11 Pro 22631, all 45 examples in one batch with nothing else running.

QuickJS did not change between batches, yet its fps moved by a median of about 2-5% from one batch to the next on this
machine, and by up to 20-40% for single examples at thousands of fps. Differences of that size, and their attribution
to one optimisation, are approximate.

### Where the time went

- **Script time** is 20-75x lower native in the script-heavy examples (raindrop-demo 2.92 to 0.07 ms a frame, fishtank
  2.90 to 0.09, godrays-room 4.42 to 0.06, world 1.78 to 0.04). QuickJS script time includes the JavaScript, the native API calls it makes and its animation, spline and camera-follow components; native counts those
  components under "sync". Marshalling op arguments out of QuickJS is at most about 0.3 ms.
- **GPU-bound scenes are equal.** When the GPU is the limit, QuickJS's script time overlaps the GPU wait, so a faster
  script does not show in fps (godrays-shed, godrays-lift, tunnel, dark-room).
- **UI, 2D and simple 3D scenes at 2,000-8,500 fps** (form, text, hello, boxes, fog-teapots) have 0.01 ms of script; the frame is the draw and the GPU, and their speed-up
  is within noise of 1.0x.

### Staged improvements

The first full run (at `41fb369`) found several examples slower native than QuickJS: the cause was the render sync
rebuilding the renderer's view of the scene every frame, not the language. The incremental render sync (`31be6440`)
fixed that (fog-world 0.86x to 2.43x, 2.57x in the final run). The Animator was then made cheap (bound tracks
`b722f24e`, `mark_moved` `6fe4775d`, buffer reuse `3abe1f58`, culling `b168dc3c`), and crowds of skinned figures (skinned-mesh frustum culling
`7d0cd929`, bone cache and packed uploads `a3dee1e0`, parallel animators `4a9a8ca7`). The per-example stages, with fps
and speed-up at each: [benchmarks.md](benchmarks.md), "Stages".

### A pure script micro-benchmark

`cargo run --release -p platypus_ts_tests --bin bench` (in `tools/`) runs the game-rules simulation (`sim.ts`, a busy state,
10,000 steps) in QuickJS, bun and native code, all with the same checksum:

| Engine | 10,000 steps | vs QuickJS |
|---|---:|---:|
| QuickJS (rquickjs 0.14) | 391 ms | 1x |
| bun (JavaScriptCore JIT) | 36.1 ms | 10.8x |
| platypus_ts (native) | 9.1 ms | 43x |

### Animator and crowds

- The Animator update on the 65-bone mannequin of fog-white-room went from 0.375 to 0.027 ms idle and 0.635 to 0.039 ms
  moving (14-16x), nearly all from binding clip curves once.
- `examples/crowd` (two sidewalks of animated mannequins, 250 or 1000 a block): at 1000 figures a block, 26.0 fps with
  `alwaysAnimate` and 29.2 fps with `cullCompletely` when one block is off screen (9.3 and 12.2 fps before the bone
  cache and the parallel animators), 98-130 fps at 250 a block; the animation update is 12.2 ms for 2,000 figures on
  all threads, the render about 21 ms. The tables: [benchmarks.md](benchmarks.md), "Animator" (with its crowd parts).

### Start-up

Native start-up is process start to first frame and includes the JIT compile. In the final run it is 0.42-0.67 s native
and 0.43-0.85 s QuickJS, except emoji (1.76 s native against 1.11 s, cold file reads right after its native build) and
md-reader (1.26 s, native only). The largest item is the headless GPU device (about 330 ms, paid by both). The
compiler's share is at most about 250 ms (emoji, about 4,700 lines), 50 ms or less for the others. A compile cache (cached IR, or cached object code) would
remove some or all of that; measurements and options: `docs/research/platypus-ts-startup-and-hot-reload.md`.

## Known limits and unverified

- **Not run in an interactive window** for these measurements: every number is from the windowless `--bench` path. The
  real-display winit runner with compiled games is untested at these frame rates, and vsync and the OS compositor are
  not part of the numbers.
- **Windows only.** Linux and macOS are untested for the native backend.
- One machine (above); GPU-bound results will differ on others.
- The compiler trusts `tsc`: a program `tsc` would reject may miscompile instead of failing.
- Start-up pays the compile on every launch (no cache yet).

## What is next

- **Dynamic `any` / `unknown`** values (decided, design in `docs/research/platypus-dynamic-values.md`; first phases only:
  `catch (e: unknown)`, untyped `JSON.parse`, `Record<string, any>`, property access).
- **A compile cache** (`docs/research/platypus-ts-startup-and-hot-reload.md`) and, for shipped games and iOS, linking the
  object into the host at package time.
- **Type checking:** `tsgo` as the optional external checker, or a `platypus-build --check` mode with the compiler's own
  diagnostics for its subset (`docs/research/platypus-ts-type-checking.md`).
- **Code review pass** after the merge to `main` (TODO.md, "Code review"), and the QuickJS removal steps.
