# Nothing left in TypeScript but types

Status: **plan for review, no code** (TODO.md M9.b2, a STOP item). Written 2026-10-19 after the user's request: "make animation
and scenes native from TS too; nothing left in TypeScript except structural type files (all generated, no `node_modules`)".

This is the end state of decision 6 in [iron-ts-engine-boundary.md](iron-ts-engine-boundary.md) section 13 ("everything in
`js/engine` is ported to Rust; what stays TypeScript is user code"), made concrete.

## 1. The end state

- **Rust owns the engine.** Every behaviour that lives in `js/engine`, `js/react` and `js/editor-ui` today is Rust, declared to
  scripts with `#[iron_api]` (compiled code calls the shims; QuickJS, while it exists, gets the typed bindings).
- **TypeScript is game code, plus types.** What the repo keeps of the engine in TypeScript is generated: the `.d.ts` of each
  `#[iron_api]` namespace (`Namespace::to_dts`), written to a folder a game's `tsconfig` points at. They are checked in or
  generated by `iron` and never edited. A game needs no `node_modules`: no `@iron/engine`, no `@iron/react`, no `react`, no
  `@types`, no bundler runtime. The compiler (`iron_ts`) reads the game's `.ts` / `.tsx` and the manifests directly.
- **UI** is the native reconciler (`iron_ui_native`, [iron-ui-native.md](iron-ui-native.md)); **gameplay** is compiled components;
  **dev loop** is `Runtime::refresh` and the compiler as the watcher ("Dev loop without Bun").
- What stays outside Rust: the user's own TypeScript, and bun only as an optional editor/test tool for the *repo*, not for games.

## 3. Order (smallest risk first, each step ships and keeps the old path working)

1. **Finish the swap-out check** (in progress): the whole sine-circle `SineDemo` compiles and runs against the declared APIs.
2. **Component property save/load** and `getComponent`/`addComponent` (needed by scenes and the editor).
3. **Animation** (`iron_animation`): port with the TS code as the oracle: run both on the same clips and compare sampled poses
   (bun for the TS side, as the stdlib tests do).
4. **Scenes**: `SceneManager`, scene JSON from the reflection tables, prefabs; compare loaded scene dumps with the TS output.
5. **Math/time/random/log/app** namespaces (small, mechanical).
6. **Physics/audio components** over the existing crates.
7. **Remove `js/engine`, `js/react`, `js/editor-ui` and the `node_modules` of games**: games build with `iron build` (compile +
   link), types come from `iron types` (writes the `.d.ts`), the editor's UI is compiled TSX.

## 4. Questions (answers change the work)

1. **Type checking without `node_modules`.** IDEs and `tsc` want the TypeScript package. Options: (a) keep a *global* `tsc`/language
   server outside the project and point it at the generated `.d.ts` (no per-game `node_modules`); (b) make `iron_ts` the checker
   (it already infers types for what it compiles; the gaps are the ones it rejects). Recommendation: (a) for editors now, (b) as
   the compiler's own diagnostics grow.
2. **QuickJS.** Keep it as the dev-mode backend (typed bindings, hot reload by re-evaluating) until `iron_ts` has a JIT dev loop,
   or drop it at step 7? Recommendation: keep until the dev loop exists; it is also the escape hatch for code the compiler rejects.
3. **Where the generated `.d.ts` live**: one file per namespace in `types/` of the game, regenerated by `iron types`, checked into
   the engine repo for the examples.

## 5. Answers (2026-10-19, from the user)

1. **Type checking:** keep `tsc`; it is pointed at the generated `.d.ts`. An `iron_ts` checker is wanted but much further away.
2. **QuickJS:** stays, for mod support and for anything that cannot use compiled TypeScript; it is a legacy path to remove when
   possible. Longer term, a TS-native runtime could absorb even QuickJS (and would likely beat generic rquickjs).
3. **Generated `.d.ts`:** written by the `iron_ts` tool, not by the game engine.
